# 처리 시간 벤치마크

아래 첫 비교표(1~2단계 후보)는 2026-10-20 합성 이미지(`scripts/bench/` 생성 스크립트), 네트워크는 일본(도쿄) 모바일 테더링, 서버는 Timely Router / Upstage 공개 API.
이후 절은 절마다 날짜·환경·사진(대부분 진단 저장소 실사진)을 적는다. 체감 기준은 「목록 완성」 시점(AGENTS.md 검증 절차 5).

| 이미지 | 내용 |
|---|---|
| `menu_test.jpg` (900×700) | 세로쓰기 短冊 8개, 한자 숫자 가격 |
| `menu_tilt.jpg` (900×1100) | 가로쓰기 14개, 종이가 7° 기울어짐 |

## 1단계 후보: Upstage Document Digitization

`POST https://api.upstage.ai/v1/document-digitization`, 이미지 1장 기준.

| 모델 | 이미지 | 시간 | 결과 |
|---|---|---|---|
| `ocr` | 세로쓰기 8개 | 3.0s | 단어 18개, 이름은 전부 정확. 세로로 쓴 가격 숫자는 줄이 흩어짐 (五八〇 → "五八〇" 는 맞으나 순서·결합 깨짐) |
| `ocr` | 가로쓰기 14개 | 3.1s | 단어 30개 전부 정확 (confidence 0.99~1.0), 기울기 무관 |
| `document-parse` | 세로쓰기 8개 | 2.8s | 메뉴 전체가 `paragraph` 1개. 항목별 좌표 없음 |
| `document-parse` | 가로쓰기 14개 | 4.1s | `heading1` + `table` 2개. 텍스트는 좋지만 좌표는 요소 단위 |

결론: 항목별 좌표가 필요하므로 **OCR(단어 단위 bbox)** 을 쓴다. Document Parse 는 이 용도에 맞지 않는다.

## 결론

- **채택: Upstage OCR (≈3s) → claude-sonnet-5-5 텍스트 전용 (첫 항목 ≈1.5s, 완료 ≈7~10s)**
- 총 처리 시간 약 10~13초로, 기존 17~33초 대비 절반 이하. 첫 항목이 화면에 뜨는 시점은 9초 → 4.5초.
- 좌표는 모델 추정 대신 OCR 단어 상자의 합집합을 쓰므로 오버레이 정확도가 근본적으로 개선된다.
- OCR 이 단어를 거의 못 찾는 경우(손글씨, 저조도)에만 이미지 직접 전달 방식으로 폴백한다.

## 2차 개선 (2026-10-20 오후): 1단계 병렬 묶음 + 2단계 상세 분리

원인 분석: 실제 메뉴판 사진(116단어)에서 Upstage OCR 은 서버 측정 1.9~4.1초였고, 전체 27.7초 중 약 21초가 LLM 출력 토큰이었다
(항목마다 설명·발음·태그를 함께 쓰면 항목당 100토큰 이상). 사용자가 본 "OCR 33초" 는 재현되지 않았다.

변경:
- 1단계는 이름·가격·좌표·아이콘만 (항목당 ≈40토큰). 단어가 60개를 넘으면 읽기 순서대로 최대 4묶음으로 나눠 병렬 호출.
- 항목 파싱을 서버로 옮겨 묶음별로 완성 즉시 전송. 목록이 완성되면 결과 화면으로 넘어간다.
- 2단계(발음·설명·태그·사진 검색어)는 10개씩 병렬 호출해 카드에 뒤따라 채운다.
- 메뉴 항목이 아닌 문구(제목, 税込 안내 등)도 1단계에서 번역해 「메뉴판 문구」로 보여준다.

| 이미지 | OCR | 첫 항목 | 목록 완성 | 상세 완료 | 이전 전체 |
|---|---|---|---|---|---|
| 세로쓰기 8개 | 2.6s | 4.5s | 6.7s | 12.7s | 10.5s |
| 실제 메뉴판 116단어 (34개 항목, 3묶음) | 3.4s | 6.3s | **10.0s** | 17.1s | 27.7s |
| 합성 277단어 (4묶음) | 5.2s | - | 16.7s | 22.4s | - |

사용자 체감 기준은 「목록 완성」이다. 실제 사진에서 27.7초 → 10.0초.

## 재현

## 대화 통역 음성 인식·번역 (2026-10-23, 로컬, macOS 합성 음성 m4a)

입력은 macOS `say` 합성 음성(한국어 Yuna·Reed, 일본어 Kyoko·Reed)을 AAC 64kbps m4a 로 만든 것(iPhone 녹음과 같은 형식). **실제 사람 목소리·가게 소음·폰 업로드 시간은 빠져 있다.** CER 은 공백·문장부호를 뺀 글자 오류율이며, 일본어는 한자 숫자 → 아라비아 숫자(一日三回 → 1日3回) 표기 차이도 오류로 센다.

| 모델 | 응답 | 한국어 CER | 일본어 CER | 무음 3초 | 비고 |
|---|---|---|---|---|---|
| Groq `whisper-large-v3-turbo` | 0.3~0.7s | 0~11% | 4~11% | 「감사합니다」·「ありがとうございました」 지어냄(`no_speech_prob` 0.00) | 채택. 언어 지정 없이도 ko/ja 구분 정확 |
| Groq `whisper-large-v3` | 0.3~0.5s | 0~11% | 5~20% | — | turbo 보다 낫지 않음 |
| Gemini `gemini-3.5-flash-lite` (오디오 입력) | 1.5~1.7s | 뜻이 바뀜(「목이 아프고」→「머리가 부러지도록」) | — | — | 탈락 |
| Gemini `gemini-3.5-flash` (오디오 입력) | 2.1~2.6s | 뜻이 바뀜(「목이 아프고 열이」→「머리가 좀 아파요」) | 1곳 오인식 | 「00:00 일본어로 작성하였습니다.」 | 탈락 |
| Gemini `gemini-3.5-transcribe` | — | — | — | — | 예비로 채택. 측정 시점에 503(수요 과다)만 와서 품질 미측정 |

인식 → 번역(Sonnet 5.5, `thinking: between_tools`) 이어 붙인 시간: 일본어 첫 글자까지 1.1~2.1s, 완료 1.8~3.4s(인식 0.3~0.4s 포함). 번역 프롬프트에 「음성 인식 오류를 먼저 바로잡기」를 넣으면 Groq 오인식 3건(목이 앞으로·알 수 있나요·2行)이 모두 고쳐졌다. `/api/talk` translate 로컬 실측: 번역문(`ja`) 필드 ≈1.8s, 완료 3.4s.

재현: `node scripts/bench/talk_stt.mjs [groq|gemini|both]` (macOS, `.env` 의 키).

### 화면 흐름 (2026-10-23, 로컬 dev, 헤드리스 Chrome 390×844, 가짜 마이크에 합성 음성 wav)

Chrome `--use-file-for-fake-audio-capture` 로 위 합성 음성(앞 1s·뒤 4s 무음을 붙인 wav)을 마이크 입력으로 넣고 버튼을 눌러 잰 시각. 「말 끝」은 녹음이 저절로 끝난 시점(말이 끝나고 1.3s 조용).

| 흐름 | 말 끝 → 받아 적기 완료(말풍선) | → 번역문 표시 | 말 끝 → 번역문 |
|---|---|---|---|
| 한국어로 말하기(「근데 제가 매운 걸…」) | 0.8s | +2.0s | **2.8s** |
| 日本語(「申し訳ございません…」) | 0.6s | +2.5s | **3.1s** |
| 글로 쓰기(한국어 → 일본어 / 일본어 → 한국어) | — | 2.0s / 2.3s(보내기 → 번역 완료) | — |
| 도우미 질문 → 답 완료 | — | 3.4s | — |

- 발음이 번역문과 다른 표현으로 나오던 것(ja 「得意じゃない」인데 pron 「니가테 쟈 나인」): 키 순서를 `ja → fixed → kana → pron` 으로 바꾸고 「kana 를 한 소리씩 한글로」 규칙을 넣어 맞췄다. 「ん」을 로마자 N 으로 쓰던 것도 받침 규칙으로 막았다(6문장 2회 확인).
- Gemini 받아쓰기 예비 경로는 이날 여러 차례(서버 PR 측정 ~ 화면 PR 마무리) 모두 503(수요 과다)이라 성공 응답 품질·지연을 재지 못했다. 무료 등급 예비 경로로서의 가용성 자체가 낮다는 신호로 기록한다([[backlog]]).

### 한국어 억양 일본어 인식과 바로잡기 (2026-10-23, 사용자 실기기 제보 「하이자라 오네가이시마스」 → 「はい、…」)

- 원어민 합성 음성(일본어 4종 × 속도 2) 「灰皿お願いします」: turbo 8/8 정확, v3 는 4/8 「はいザラ…」, Whisper `prompt`(상황 설명)는 개선 없음 → 모델·프롬프트 그대로.
- 한국어 합성 음성이 한글 「하이자라 오네가이시마스」를 읽게 하면(억양 재현): 「はい、ざら」「はい、じゃあ」「アイジャラ」로 인식 → **원인은 음성 인식(억양)**.
- 번역 단계 바로잡기, 이자카야 맥락 2회씩: 이전 프롬프트는 「はい、ざら」 → 「とりあえず生」·「麦茶」·「ざる」, 「アイジャラ」 → 「アイスジャスミン茶」로 **지어냄**. 새 프롬프트(소리가 거의 같은 말까지만)는 「はい、ざら」·「アイジャラ」 → 灰皿 4/4, 「はい、じゃあ」·「はい、かしこまりました」는 그대로.
- 프롬프트 예시에 없는 억양 문장(오시보리·토리아에즈 나마·오카이케·하이 소데스·이마 이이데스카): 회귀 없음. 「오히야」(お冷) → 「お部屋」는 모음 하나 차이라 고치지 않음(남은 한계).
- 추가 확인(같은 날, 사용자 「몇 번을 말해도 はい、로 끊긴다」): 한국어에는 z 소리가 없어 「하이자라」는 일본어 귀에 「はいじゃら」로 들린다. Whisper 는 이를 흔한 문장 「はい、じゃあお願いします」로 맞추는데, 이건 멀쩡한 문장이라 번역 단계 바로잡기도 손댈 근거가 없다.
  - Whisper `prompt` 에 식당 단어 목록(灰皿·お冷·おしぼり…)을 넣어도 억양 5종 중 1건만 灰皿(나머지 「はい、じゃら」「アイジャラー」). 오히야·토리자라·하시도 그대로 틀림.
  - Gemini `gemini-3.5-flash` 에 「한국어 억양 일본어」라고 알려 받아 적게 하면 더 나쁨(「あいざわ」「お会計」「もう一つ」 등, 1.7~2.5s).
  - 결론: 무료 음성 인식으로는 억양 일본어를 못 살린다. 일본어 버튼은 원어민(점원)용, 사용자는 한국어로 말하는 기본 흐름을 쓴다. 개선 후보는 [[backlog]].

## 한국어 사진 기준선 (2026-10-31, 로컬 dev, 역방향 한→일 착수 전)

역방향(일본인 사용자가 한국어 메뉴판·안내문을 찍는 흐름) 착수 전에 **지금 그대로의 파이프라인**에 한국어 사진을 넣어 OCR 품질과 현재 프롬프트의 반응을 쟀다. 사진은 Wikimedia Commons CC 실사진 5장(한식 코스 차림표, 프렌치 런치 코스(불·한 병기), 재난위험시설 안내판, 편의점 간판, 비데 조작 패널)과 가격 표기를 모은 합성 메뉴판 1장(`scripts/bench/make_menu_ko.py`). Upstage Document OCR 문서 기준 한글은 정식 지원, 한자·가나는 beta.

| 사진 | 단어 | 한글 비율 | 회전/기울기 | OCR | 현재 판정 | 항목/문단 | 목록 완성 |
|---|---|---|---|---|---|---|---|
| 합성 메뉴판(18항목, 9,000·9.0·15,000원·1인분) | 77 | 0.50 | 0 / 0° | 5.6s | other | 11 / 8 | 11.9s |
| 한식 코스 차림표(가격 없음) | 33 | 0.86 | 0 / 0° | 1.5s | menu | 9 / 0 | 5.8s |
| 프렌치 런치 코스(불·한 병기, 95.) | 47 | 0.20 | 0 / -1.5° | 1.5s | menu | 9 / 3 | 6.7s |

- **OCR 은 한국어를 그대로 읽는다.** 가격 조각(「9,000」「9.0」「15,000원」「(1인분」「180g)」)이 깨지지 않고, 단어 상자도 글자에 맞는다(오버레이 캡처는 보고 아티팩트). 첫 호출 5.6s 는 콜드 스타트, 이후 1.4~1.8s.
- **현재 프롬프트는 한국어 메뉴판을 못 다룬다(예상대로).** 합성 메뉴판은 `other` 로 판정돼 첫 묶음(식사 6항목)이 문단으로 빠지고, 남은 11항목도 가격이 전부 null(`price_jpy` 의미라 원화를 버림). 긴 안내판은 문단 3개만 내고 멈췄고, 세로 라벨 패널은 문단 0개. → 방향 매개변수 프롬프트(PR2)의 비교 기준.
- 한국 메뉴판 고유 표기: 천 단위 생략(「9.0」= 9,000원), 「(1인분)」「(2인 이상)」「180g」 단위가 이름 옆에 붙는다. 역방향 1단계 규칙에 넣는다.

재현: `pnpm dev` 후 `python3 scripts/bench/ko_bench.py <초대 코드> <출력 폴더> <사진…>` → `scripts/bench/ko_overlay.py` 로 단어 상자 캡처.
